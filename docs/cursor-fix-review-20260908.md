## 1. P1：样本来源识别混淆试剂、来源与否定语境

位置：`backend/app/pipeline/source.py:9`，以及 screening/assessment 中来源规则的调用处。

当前 `source_kind()` 将 title、source_name、characteristics 和 protocol 序列化后整体匹配关键词。已用当前函数复现：

```python
source_kind({
    "source_name": "HEK293T",
    "protocol": "Cells were maintained in DMEM supplemented with 10% fetal bovine serum.",
})  # 当前为 primary，错误

source_kind({
    "source_name": "PBMC",
    "protocol": "No cell lines were used.",
})  # 当前为 cell_line，错误
```

修改要求：

- 分开处理明确的样本材料字段和实验步骤，不能把培养液、血清添加剂等当成采集材料。
- 处理否定表达；出现 `cell line` 字符串不等于样本来自细胞系。
- 保留明确 PBMC、胰岛、脑区等原代材料识别，避免修复后再次全部变成 unknown。
- 明确细胞系、iPSC、类器官、异种移植和培养语境之间的边界；证据不足或矛盾时保持 unknown。
- 同时审查规则可独立通过硬条件的路径，不能让错误来源规则绕过核验。

验收：覆盖以上两个反例、真实原代材料、培养来源、否定和矛盾语境；HEK293T 不得为 primary，明确 PBMC 不得仅因否定句被判成 cell_line。补充从规则到最终分类的回归，不能只测关键词函数。

## 2. P1：核验队列与 API/Excel 可用样本不一致

位置：

- `backend/app/pipeline/assessment.py:488` 附近的 `_restrict_to_common_subset()`。
- `backend/app/api/__init__.py:489` 的 `applicable_gsms`。
- `backend/app/exporters/service.py:96` 的 `applicable_gsms`。

当前核验允许疾病证据只列病例，groups 代表完整病例/对照队列；但 API 和导出仍对所有有 GSM 的最终条件取交集，连软条件和 unknown 条件的集合也可能参与。

用 `data/source-live-medium8-20260907/targeted-merged.json` 的真实模型输出，按当前 API/导出算法计算得到：

| GSE | groups 队列 GSM 数 | API/导出交集 GSM 数 |
| --- | ---: | ---: |
| GSE325391 | 18 | 12 |
| GSE153855 | 11 | 5 |
| GSE266852 | 7 | 3 |

这里丢失的是对照样本；上述数字来自当前算法对保留输出的回放，不能说历史 Excel 已由最终代码重新生成。

修改要求：

- 统一“最终可用比较队列”的计算，供核验、详情和导出使用，避免各自实现不同含义。
- 区分病例疾病证据与完整比较队列；不能简单取所有条件交集，也不能改成无条件并集。
- 只在样本同时符合适用硬条件、覆盖所需分组时保留队列。
- 审计当前 groups/donors 覆盖其他条件集合的逻辑；当前 `_sample_fits_all_hard()` 只检查物种、技术、来源和组织，必须防止年龄、性别、自定义硬条件或供体条件在不同子集分别通过。
- GSM 数量不等于独立供体数量；过滤队列后需保证分组及供体门槛仍成立。

验收：API 和 Excel 返回一致的可用队列；保留有效对照；混合物种/技术、其他疾病、硬条件子集不相容、供体不足时不得错误推荐。添加覆盖 API/导出的集成回归，不只测试辅助函数。

## 3. P1：切换课题后保留旧课题结果与导出目标

位置：`frontend/src/App.tsx:99`、创建课题成功回调、`:240` 的课题切换、`:380` 的导出。

已在浏览器中用受控 API 响应复现：打开有运行记录的课题 A，再切到无运行记录的 B，输入框显示 B，但 A 的运行结果仍可见。导出使用旧的 `current.id`，因此会导出 A。

修改要求：

- 切换或创建课题时同步处理 runId、selected 和相关详情状态。
- 仅允许当前课题所属运行显示结果和执行导出、暂停、恢复、取消。
- 正确处理新课题无运行、有运行、快速连续切换以及异步响应晚到的情况。

验收：新增浏览器回归，覆盖 A→无记录 B、A→有记录 B、创建新课题、快速切换；断言结果与操作请求的 runId 属于当前课题，而不仅仅检查标题改变。

## 4. P1：先全部初审再全部复核，预算消耗后可能没有完成结果

位置：`backend/app/pipeline/engine.py:556` 的 `step_assess()`、`:617` 的 `step_verify()`，相关预算和任务检查点逻辑。

当前逐个初审全部目标，最后才进入复核。最近三次真实 Medium 测试将深核目标设为 8，其他预算保持 Medium 默认；结果如下：

| 课题 | 候选 | 深核下载 | 完整核验 | 主运行推荐 | token |
| --- | ---: | ---: | ---: | ---: | ---: |
| AD 原代脑组织 | 150 | 8 | 5 | 0 | 143824 |
| T2D 原代胰岛 | 150 | 8 | 0 | 0 | 136454 |
| RA 原代 PBMC | 106 | 8 | 7 | 0 | 111976 |

三次均为 partial；前两次因剩余预算不足，RA 因检索截断。不能把推荐为零全部归因于调度，来源和队列门禁当时也存在问题。

修改要求：

- 优先按候选优先级完成单条“初审→复核→最终合并”，再进入下一条。
- 为一条完整核验合理预留预算，纳入输出和可能的格式修复开销；不要单纯提高默认 token 上限。
- 初审和复核继续使用独立审查上下文；调度变化不能让复核变成照抄初审。
- 保留检查点、暂停恢复、取消、等待凭据和失败处理；恢复不能重复收费或漏掉候选。
- 预算结束时保留已完成结果，并清楚区分未开始、初审完成、复核完成等状态。

验收：用受控用量的模型 mock 覆盖“预算只够完成少数条”的情形，确认先有完整结果；覆盖中途恢复、取消、模型错误和预算停止；用量记录完整。mock 通过不等于真实付费链路通过。

## 5. P2：候选排序不够重视硬组织和来源条件

位置：`backend/app/pipeline/ranking.py:20` 的 `relevance()`、`:72` 的 `select_deep_targets()`。

当前标题与摘要合并后出现目标组织词即加分，缺少对背景提及与实际样本来源的区分。上次脑组织任务选到 GSE248417 全血研究；胰岛任务也将 GSE236191 心脏活检研究纳入有限深核名额。

修改要求：

- 区分直接样本材料证据、标题提示和背景描述，硬组织/来源条件应影响深核优先级。
- 对明确不匹配降权；摘要缺失或模糊不能直接当作排除依据。
- 模型研究是否适合应结合结构化 spec，不能只看 original_request 是否含英文 model。
- 保留多样性策略，但避免多样性让明显低相关候选挤掉高相关候选。
- 页面选择理由应与实际评分一致。

验收：构建包含正确组织、背景提及、明确错误组织、组织未知、原代与模型来源的排序用例；检查深核目标选择及实际处理顺序，不只检查分数。
